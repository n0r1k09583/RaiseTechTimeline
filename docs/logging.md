# ログ設計と監視

Webアプリは「作って終わり」ではない。公開したあとも動き続け、障害の痕跡は **ログに残る**。料理に例えるなら、盛り付けて出すまでが実装、食べたあとも体の中に残り続けるのが運用である。

課題は **`backend/logs/` のファイルを開いて確認する** ことまで。Datadog などの監視 SaaS は紹介にとどめ、**このリポジトリには入れない**（課金・常時稼働を増やさない）。

関連: [テスト](./testing.md)、[機能定義書](./FEATURES/機能定義書.md)（要件の「ログ」）、起動は `backend` で `.\mvnw.cmd -Dmaven.test.skip=true spring-boot:run`

---

## なぜログが要るか

画面の 500 は「サーバーで問題が起きました」だけ返す。原因はログ側に書く。AI 時代はログを読ませて切り分けできるが、**何をどのレベルで残すか** は開発者が決める。パスワードや JWT を出してしまうと、あとから読めない（読んでいけない）ログになる。

---

## 種類

| 種類 | このアプリでの置き場 | 見ること |
|------|----------------------|----------|
| アクセスログ | `logs/access.*.log`（Tomcat） | 誰がどの URL に何ミリ秒で、ステータス何番か |
| アプリケーションログ | `logs/application.log` | ログイン成功／失敗、投稿作成、権限なし |
| エラーログ | `logs/error.log`（ERROR 以上だけ） | 未処理例外、画像保存失敗 |

コンソールにも同じアプリケーションログが出る。ファイルは再起動後も残る。

---

## レベル

| レベル | いつ使う | 例 |
|--------|----------|-----|
| DEBUG | 調査するときだけ。既定は出さない | 分岐の途中 |
| INFO | 正常な節目 | ログイン成功、投稿作成 |
| WARN | 想定内の失敗。すぐ落とさない | ログイン失敗、他人の投稿を消そうとした、トークン無し |
| ERROR | 想定外。人が見る | 未処理例外 |

本番の既定は `INFO`。調べるときだけ `application.yml` の `logging.level.com.raisetech.timeline` を `DEBUG` にする。

---

## このリポジトリでの決め事

- パスワード・生の JWT・リフレッシュトークンは **ログに出さない**
- ログイン失敗は理由（ユーザー不在／パスワード違い）をログでも分けない。画面と同じく列挙対策
- 失敗時は `email=` や `userId=` / `postId=` まで。リクエスト本文は出さない
- ローテーション: アプリケーション 7日・10MB、エラー 14日
- テストは `logback-test.xml` でコンソールのみ。`logs/` に書かない

設定: `backend/src/main/resources/logback-spring.xml`、`application.yml` の `logging` と `server.tomcat.accesslog`。

確認手順:

1. `backend` で起動する
2. ログインをわざと失敗させる
3. `backend/logs/application.log` に `ログイン失敗` があり、パスワードが無いことを見る
4. `backend/logs/access.*.log` に `POST /api/login` とステータスがあることを見る

## Datadog など（導入しない）

本番ではログとメトリクスを Datadog / CloudWatch に送ることが多い。AI がそのストリームを読んでアラートする、という話もある。中級編の課題は **ファイルを自分で開く** こと。ツールのアカウント作成は不要。
